# Техническое задание: «Деньги по плану»

Версия: 1.2. Дата: 17 октября 2026 года. Язык интерфейса: русский. Учтены внешняя проверка требований (раздел 24) и обратная связь пользователя по первому экрану и дизайну (раздел 25).

Документ описывает первую рабочую версию семейного финансового планировщика. Он имеет приоритет над предыдущим `concept.md` при любых расхождениях. Реализация страницы не входит в текущий этап: результат этого этапа — данное ТЗ.

## 1. Назначение и обязательный результат разработки

Продукт помогает семье учитывать имеющиеся деньги, поступления и расходы, планировать обязательства, соблюдать лимиты, копить на несколько целей, учитывать вклады и кредиты. Основные показатели главного экрана: «Общий баланс» и «Можно потратить до конца месяца».

Разработчик должен предоставить ровно три исполняемых файла приложения: `index.html`, `style.css`, `script.js`. Нативные HTML, CSS, JavaScript; без внешних runtime-зависимостей, UI-фреймворков, CDN и внешних шрифтов. Для запуска готовой страницы установка Node.js/npm и сборка не нужны. Графики — SVG или Canvas с текстовой легендой. Markdown-документы не считаются файлами приложения.

В ходе разработки разрешены отдельные исходные ES-модули и сборщик как инструменты разработчика. При выборе сборки она должна выдавать один `script.js` без code splitting, внешних импортов и дополнительных runtime-файлов; CSS — один отдельный `style.css`. Исходники и конфигурацию сборки сохранить в отдельном каталоге разработки, указать воспроизводимую команду сборки в сопроводительной документации. Этот каталог не является четвертым файлом готовой страницы. Модульность в разработке рекомендована для расчетов и хранилища; установка и использование сборщика не являются требованием к пользователю. Не публиковать исходные тестовые данные и секреты в итоговом бандле.

Обязательны: хранение в браузере, локальная регистрация и вход, роли членов семьи, две темы, компьютерный интерфейс, ручные курсы, голосовой ввод доходов и расходов. Экспорт, импорт и мобильная адаптация не требуются.

### 1.1. Граница локальных аккаунтов

Три статических файла и браузерное хранилище позволяют реализовать локальные учетные записи одного семейного пространства на одном origin в одном профиле браузера. Первый зарегистрированный пользователь создает семью и становится владельцем. Следующих пользователей добавляет владелец; публичной регистрации в существующую семью нет.

Это разделение действий внутри приложения: оно предотвращает случайные изменения через интерфейс, но не обеспечивает серверной защиты от владельца устройства, изменения JavaScript или прямого доступа к хранилищу через инструменты разработчика. Данные бюджета в этой версии не шифруются. Не называть локальную авторизацию полноценной облачной системой безопасности.

На телефоне, другом компьютере, в другом браузере или профиле будет отдельное хранилище. Общие аккаунты и синхронизация между устройствами потребуют отдельного сервера и базы данных и относятся к следующей версии. Открытие тех же трех файлов на другом устройстве не переносит бюджет.

Поддерживаемый способ запуска — статическая раздача с постоянного адреса localhost или HTTPS. Наличие сервера статических файлов не означает наличие серверной базы бюджета. Прямое открытие через `file://` не является приемочным режимом: показать инструкцию запуска, если нужные API недоступны. Целевые браузеры — актуальные стабильные Chrome и Edge на Windows на дату реализации; остальные поддерживаются по возможности. Голос проверяется отдельно по доступности API.

### 1.2. Решения по неуточненным деталям

Ниже зафиксированы продуктовые решения для однозначной реализации: роли и очередь подтверждения; ручное подтверждение платежей по умолчанию; точность валют; расчетные модели депозитов и кредитов; отсутствие налогового калькулятора; ограничения редактирования прошлых дат. Это принятые в ТЗ решения, а не дополнительные дословные требования пользователя. Реализовать их без расширения объема работ.

## 3. Роли, учетные записи и права

В семье один владелец. В первой версии передача владения не нужна. Нельзя удалить или заблокировать владельца. Число участников не ограничивать искусственно.

| Действие | Владелец | Участник | С подтверждением | Наблюдатель |
|---|---|---|---|---|
| Смотреть общий бюджет, операции, цели, графики | Да | Да | Да | Да |
| Добавлять фактический доход/расход/возврат | Напрямую | Напрямую | Заявка | Нет |
| Использовать голос | Да | Да | Заявка | Нет |
| Переводить и обменивать деньги | Да | Да | Нет | Нет |
| Править/отменять финансовые записи | Все | Свои за сегодня, без зависимых записей | Только свою ожидающую заявку | Нет |
| Изменять чужие или старые записи | Да | Запрос владельцу | Запрос владельцу | Нет |
| Подтверждать заявки | Да | Нет | Нет | Нет |
| Настраивать кошельки, категории, курсы, планы, лимиты, цели | Да | Нет | Нет | Нет |
| Управлять депозитами, кредитами и займами | Да | Нет | Нет | Нет |
| Управлять профилями и журналом | Да | Нет | Нет | Нет |
| Менять собственный пароль и тему | Да | Да | Да | Да |

Все участники видят общие семейные суммы; скрытых счетов и индивидуальных бюджетов нет. Участник с подтверждением подходит для ребенка или человека, чьи записи необходимо проверять. Его заявка не влияет на баланс, лимиты и отчеты до одобрения.

Профиль: UUID, отображаемое имя 1–50 символов, уникальный логин 3–40 символов, пароль, роль, статус active/blocked. Логин: латинские буквы, цифры, точка, дефис, подчеркивание; сравнение без учета регистра. Пароль: 8–128 символов, без требования специальных символов, подтверждение при создании.

Пароли не хранить открыто: Web Crypto PBKDF2-HMAC-SHA-256, случайная соль 16 байт на пароль, 600 000 итераций, результат 32 байта; сохранять параметры вместе с результатом. Вызывать асинхронный `crypto.subtle.deriveBits`, не выполнять 600 000 проходов собственным циклом JavaScript. Вычислять проверочное значение только при создании/смене/сбросе пароля и входе, не при каждой финансовой команде. Пока идет проверка, показать индикатор и блокировать повторное нажатие; искусственной задержки поверх вычисления не добавлять. На целевом компьютере измерить время, не обещая одинаковую скорость на всех устройствах.

Это способ хранения проверочного значения, не шифрование бюджета и не защита от обхода интерфейса через DevTools. `SubtleCrypto` — API, через который уже вызывается PBKDF2, а не альтернативный способ авторизации. Один общий PIN не вводится: он не позволяет разделять авторство и права разных членов семьи. При отсутствии Web Crypto вход и регистрацию не подменять хранением открытых паролей; показать сообщение о неподдерживаемом режиме запуска.

Первый запуск: логин, пароль, повтор пароля и выбранная дата начала → сразу открыть обзор бюджета. В форме нет имени, названия семьи, выбора часового пояса или блока первого кошелька. Имя владельца для отображения и авторства автоматически берется из логина. Счета и начальные остатки добавляются внутри после регистрации через раздел «Кошельки» или действие на пустом обзоре. Не создавать при регистрации фиктивный счет или деньги. Отображаемый заголовок общего пространства — «Мой бюджет».

Сеанс хранится только в памяти вкладки; после перезагрузки требуется вход. Автоблокировка после 15 минут бездействия и ручная кнопка «Заблокировать». Перед фиксацией изменения проверять актуальную роль и блокировку профиля. Пять неверных паролей подряд блокируют попытки этого логина на 60 секунд; это локальная защита интерфейса. Сообщение: «Неверный логин или пароль».

Владелец может сбросить пароль участнику с обязательной сменой при следующем входе, поменять роль и заблокировать доступ. Авторство старых операций сохраняется; использованные профили архивируются, не удаляются физически. Сброс пароля владельца по email, секретному вопросу или скрытой кнопке не реализуется. На регистрации явно сообщить, что удаленного восстановления нет.

## 4. Общие правила дат, сумм и сохранения

### 4.1. Даты

Дата начала выбирается пользователем, обязательна и не заполняется автоматически. Кнопку «Сегодня» можно предоставить как осознанное действие. Разрешены прошлая, текущая и будущая даты. Будущая дата включает состояние «Подготовка»: можно настроить начальные остатки, планы, лимиты, цели и профили; фактические операции запрещены до ее наступления.

Доходы и расходы до даты начала не вводятся. Для счетов, вкладов и кредитов, существовавших раньше, вводятся остатки на начало учета, без восстановления прошлой истории. Даты исторического открытия таких договоров могут быть раньше начала учета.

Владелец может менять дату начала, пока нет фактических операций, подтвержденных начислений и движений резервов. После первой такой записи дата заблокирована. Нельзя скрыто удалить историю при изменении даты.

Сохранять даты как `YYYY-MM-DD`, время аудита как ISO UTC, время пользовательской операции как `HH:mm`. При создании бюджета автоматически определить часовой пояс браузера и сохранить его IANA-идентификатор; это внутренний параметр расчетов, а не поле пользователя. Не показывать его выбор или редактирование в регистрации и настройках. Все границы отчетов и расписания считать в сохраненном часовом поясе, а не по часовому поясу случайного устройства. Уже сохраненный часовой пояс существующего бюджета при обновлении интерфейса не менять.

Фактическая дата не может быть позже сегодняшней даты семьи. Будущая запись сохраняется только как план. Дата финансового исправления — дата исходного события; фактическое время исправления всегда остается в журнале.

### 4.2. Деньги и точность

Суммы вводятся положительными; направление задает тип операции. Принимать запятую или точку как десятичный разделитель и пробелы как разделители тысяч. Не принимать экспоненциальную запись, NaN, Infinity, неоднозначное смешение разделителей, минус и нулевую сумму операции.

В хранилище деньги — строка целого числа минимальных единиц. RUB/USD/EUR/USDT — 2/2/2/6 знаков; BTC — 8, ETH — 18; для пользовательского тикера выбрать точность 0–18 при создании, затем не менять. Вычисления денежных величин — BigInt/фиксированная десятичная арифметика; не суммировать деньги через двоичный Number. Конверсия в Number допустима для геометрии графика после расчета итогов.

Курсы и проценты хранить десятичными строками. Курс до 12 знаков после запятой, процент до 6. Округление денежных итогов — half-up до точности валюты. Хранить округленные фактические проводки; расчет процентов накапливать с дополнительной точностью и округлять при выплате/капитализации. Отображение — `ru-RU`, код валюты рядом с неоднозначным символом. Пустое значение не равно нулю.

### 4.3. Атомарность и история

Действие с несколькими проводками сохраняется полностью либо не сохраняется вовсе: перевод, обмен, платеж кредита, депозит, расход с резервом. Изменение состояния и запись журнала — одна транзакция хранилища. Успешное сообщение показывается только после завершения транзакции.

Финансовые записи не удалять физически: отмена или исправление создает новую ревизию с причиной, а прежняя версия доступна владельцу. Аналитика учитывает только актуальную подтвержденную ревизию. Это необходимо для разбора семейных ошибок и зависимых платежей, а не для имитации защищенного серверного аудита.

Журнал компактный: actorId, entityId, действие, время, причина и только измененные поля с прежними/новыми значениями. Не копировать целиком семью, проводки или весь бюджет в каждую запись. Для финансового исправления журнал ссылается на неизменяемые ревизии операции; их полное содержимое повторно в audit не сохраняется. Для создания/отмены достаточно идентификатора и краткого резюме. Изменения темы, фильтров, посещения экранов и неуспешные попытки голосового распознавания не журналируются. Пароли, соли, проверочные значения паролей и аудио не включать даже в измененные поля. Финансовые ревизии и решения по заявкам не удалять автоматически; объем показывать владельцу, ошибки квоты обрабатывать по разделу 18.1. Кнопку «Отменить» для только что созданной независимой операции можно дать как быстрый путь к той же команде отмены, не как замену истории.

Формы — модальные окна или боковые панели. Постоянные подписи полей, звездочка обязательных полей, ошибки рядом с полем, резюме результата перед сложными действиями. Закрытие несохраненной измененной формы требует подтверждения. Удаление, отмена, закрытие договора и действия с недостатком средств имеют отдельный обзор суммы и последствий.

## 6. Кошельки и начальные остатки

Типы: `cash`, `bank_account`, `card`, `crypto`. Владелец вводит собственное название, валюту, стартовый остаток, необязательный комментарий. Стартовый остаток неотрицательный. По умолчанию кошелек ликвидный; для заблокированных или долгосрочных средств можно отключить «Доступен для текущих расходов». Криптокошелек по умолчанию не доступен для повседневных трат, флаг можно изменить.

Нет жесткого лимита в 10 кошельков: приемка минимум на 25. Кошелек — один отдельный баланс в одной валюте; общая карта, отражающая тот же банковский счет, не должна дублировать его. В форме пояснить: «Добавляйте только отдельные остатки, чтобы не посчитать одни деньги дважды».

Название уникально среди активных кошельков без учета регистра и внешних пробелов. Архивирование разрешено при нулевом балансе, отсутствии активных резервов и будущих привязок. Кошелек с историей не удалять физически. Переименовывать можно; валюту после первой финансовой записи менять нельзя.

Стартовый остаток можно скорректировать владельцу с причиной и пересчетом истории. При наличии зависимых резервов, выплат или недостаточного остатка показать затронутые записи и запретить исправление до устранения зависимостей; нельзя молча обнулять их. Новые деньги, появившиеся после старта, оформляются доходом, не правкой стартового остатка.

Баланс кошелька на дату = стартовый остаток + все подтвержденные поступления − все подтвержденные списания с effectiveDate не позже этой даты. Ожидающие заявки и планы его не меняют. Отрицательный остаток допускается только при явном подтверждении пользователем с правом прямой записи и причине; сигнал о нехватке сохраняется.

## 7. Операции, категории, пометки

### 7.1. Формы и категории

Доход: сумма, валюта из кошелька, кошелек, дата/время, категория, необязательный член семьи и комментарий до 1000 символов. Расход: те же поля плюс необязательный регулярный шаблон, связь с планом и использование резерва цели. Автор операции и человек, к кому относится покупка, — разные поля.

Доходы по умолчанию: зарплата, аванс, отпускные, подарок, подработка, продажа вещей, выигрыш/лотерея, проценты по депозиту, прочие поступления. Расходы: продукты, транспорт, одежда, жилье и коммунальные услуги, здоровье, развлечения, кредиты, подписки, непредвиденные, банковские комиссии, прочие комиссии, прочее. Категории процентов, кредитов и комиссий системные и имеют стабильные systemCode.

Свои категории создает владелец: название, тип income/expense, цвет из спокойной палитры. Использованные категории архивируются. Удалить категорию без использования можно. Названия уникальны внутри типа. Не превращать расходную категорию в доходную после использования.

Разделенный расход — один платеж с несколькими строками категорий и необязательными членами семьи. Сумма строк строго равна общей сумме. Кошелек, валюта, дата и получатель общие. Баланс списывается один раз; лимиты и диаграмма используют строки.

### 7.2. Возврат покупки

Возврат привязывается к исходному расходу и строкам категорий; можно выбрать счет получения в той же валюте. Частичный возврат разрешен, суммарно не больше невозвращенной исходной суммы. Возврат не является доходом: он уменьшает расходы на фактическую дату возврата, не переписывая прошлый период. Для аналитики возвращаемая часть использует рублевую оценку исходного расхода; отличие от текущей оценки денег относится к переоценке.

Изменение/отмена исходного расхода блокируется до отмены зависимых возвратов. Для возврата покупки до начала учета использовать категорию дохода «Возврат прошлых покупок» с заметкой; он не уменьшает несуществующую историю расходов.

### 7.3. Перевод и обмен

Перевод между счетами одной валюты: счет списания, счет получения, сумма, дата, комментарий. Разные счета обязательны. Сумма приходит полностью; комиссия — дополнительный отдельный расход на выбранном счете, связанный с группой.

Обмен: два счета с разными валютами, отданная сумма A, фактический курс K в явно подписанном направлении «1 [валюта списания] = K [валюта получения]», полученная сумма B, дата, комиссия. Пользователь может вводить A и K (B рассчитывается) или A и B (K рассчитывается). Последний измененный режим считается источником истины; несоответствие третьего поля показывается, молчаливой подмены нет. На подтверждении первичны фактические A и B, эффективный курс B/A сохраняется; исходный заявленный K можно сохранить как справочный.

Любая пара обменивается напрямую: например, USD → EUR по фактическим A/B или прямому K. RUB не является промежуточной валютой сделки, даже если отчеты ведутся в RUB. Отсутствие справочного курса USD/RUB или EUR/RUB не мешает обмену: неполной будет только рублевая оценка. Изменение справочных RUB-курсов никогда не меняет фактически полученное B или сохраненный прямой K. Автоматически строить все кросс-курсы по одной сделке не нужно.

Комиссия не включается в A или B скрыто: форма пишет «Суммы без отдельной комиссии». Комиссия имеет собственную валюту и кошелек, в том числе отличный от валют двух сторон. Вся группа атомарна. Рубли, USD, EUR и криптовалюты обмениваются по одной схеме. Реальный обмен наличными поддерживается так же, без привязки к банку.

Комиссии банка при переводе, снятии наличных и банковском обмене по умолчанию идут в системную категорию «Банковские комиссии» (`bank_fees`); комиссии частного обмена, криптосети и иных посредников — «Прочие комиссии» (`other_fees`). Тип комиссии явно выбирается/подтверждается в форме, а не выводится только из валюты. Обе категории входят в общую сумму расходов, график категорий и общий лимит: это реальные затраты семьи. В аналитике есть фильтр «Комиссии» и раздельные итоги банковских/прочих комиссий. Основная сумма снятия наличных — перевод с банковского счета на наличный кошелек, расходом является только комиссия. Комиссия, уже включенная в кредитный платеж, остается в его детализации и не создается вторым расходом категории bank_fees; ее можно показать в справочном итоге комиссий без прибавления к расходам повторно.

Основные части перевода/обмена не попадают в доходы и расходы, комиссия попадает в расходы. Отмена отменяет всю группу. Операция обмена не обновляет справочный курс всех остатков автоматически; по отдельной галочке можно создать ручной курс RUB-оценки, когда одна сторона RUB, с явным подтверждением.

### 7.4. Список и исправления

Таблица: дата, тип/статус, категория, счет, сумма/валюта, член семьи, комментарий, автор. Фильтры: диапазон дат, тип, кошелек, категория, член семьи, автор, статус; поиск по названию/комментарию без учета регистра. По умолчанию новые сверху, порции по 50, кнопка «Показать еще».

Перед исправлением пересчитать все последующие зависимые остатки. Запись, от которой зависят возвраты, депозитный расчет, кредитный график или резервы, нельзя исправить обычной формой: открыть связанный модуль и объяснить порядок отмены. Любое сохранение повторно проверяет права и ревизию данных.

## 8. Курсы и оценка валют

База отчетов — RUB; курс RUB всегда 1. Владелец задает датированный курс «1 единица валюты = N RUB». Значение строго положительное. Криптовалюта не привязана к доллару автоматически: USDT имеет собственный ручной курс RUB.

Для исторической операции использовать последний введенный курс с датой не позже ее даты; курс и рублевая оценка фиксируются в записи. Если подходящего курса нет, при записи запросить его либо сохранить флаг неполной оценки; итог отчета явно неполный. Новый текущий курс не переписывает исторические операции. Отдельного массового пересчета истории в первой версии нет.

Текущий общий баланс оценивает остатки по последнему курсу не позже сегодняшней даты. Показать дату каждого курса и предупреждение, если он старше семи дней, без автоматической загрузки. Курс будущей даты не применяется сегодня. Неполный итог отображается «Не менее … ₽ + суммы без курса», а не как полноценная сумма.

Доходы/расходы за период — исторические рублевые оценки. Текущий баланс может меняться из-за курса: это не доход/расход. Историческая общая оценка использует остатки и курсы на конец дня периода. Для сверки отображать отдельно переоценку и прочие денежные движения.

## 9. Планы, повторения, лимиты и прогноз

Планирование добровольно: нулевое число планов и лимитов — нормальный сценарий. Будущий доход не считается полученным. План имеет тип, дату, категорию, счет/валюту, ожидаемую сумму, комментарий, статус planned/partially_fulfilled/fulfilled/skipped/cancelled и связи с фактическими исполнениями. План отличается от лимита: лимит — разрешенный объем категории, а план — ожидаемая денежная операция или явно заданный бюджет предстоящей покупки. Один и тот же месячный лимит продуктов не создает обязательство O автоматически.

Для обычного дохода/расхода разрешить несколько частичных исполнений одного плана. Остаток плана = max(0, ожидаемая сумма − сумма привязанных действующих исполнений). При меньшем факте форма предлагает «Это часть плана, остаток еще ожидается» (по умолчанию) или «Закрыть план этой суммой» (фактическая стоимость оказалась меньше). Во втором случае остаток явно списывается как отмененное ожидание, а не расход. При факте больше плана остаток нулевой, разница — превышение плана, не новое обязательство. Для договора кредита/депозита сохраняются специализированные правила разделов 11, 12 и 23.4; частичная оплата кредитной строки по-прежнему не поддерживается.

Одна обычная фактическая операция может быть связана максимум с одним обычным планом. Валюта исполнения и плана должна совпадать; другой фактический кошелек в той же валюте разрешен и сохраняется. Исполненные части не получают новый исторический курс плана: факт имеет собственный курс, а еще ожидаемый остаток оценивается текущим. При отмене/исправлении факта его связь и остаток плана пересчитываются атомарно. Возврат покупки не возобновляет закрытый план автоматически; владелец при необходимости создает новый план.

Регулярность первой версии — ежемесячная, для доходов и расходов по желанию. Поля: дата начала, день месяца 1–31, необязательная дата окончания, тип, сумма, счет, категория, режим подтверждения. На короткий месяц дата сдвигается на последний день, следующий месяц сохраняет исходный день. Будущие экземпляры строятся на 12 месяцев вперед или до даты окончания; план дальше горизонта строится при просмотре.

По умолчанию расход требует «Оплачено», доход — «Получено». При открытии из плана форма уже содержит связь с ним. При вводе из общей формы предложить подходящие неоплаченные планы по валюте, категории, счету и близкой дате; выбор делает пользователь, автоматического совпадения только по категории не делать. Если пользователь оставляет похожий план несвязанным, явно сообщить, что это отдельная трата и исходный план останется в обязательствах. Для заявки это решение подтверждается владельцем.

Опция автоматической фиксации включается отдельно в каждой серии владельцем; пояснение: это запись в учете, не подтверждение банка. Она фиксирует только непокрытый остаток экземпляра, а не исходную сумму повторно; при закрытом экземпляре ничего не проводит. При нехватке денег автоматическая запись не уходит в минус: остается ожидающей с ошибкой до ручного подтверждения. У пользователя с подтверждением такой опции нет.

Обработка пропущенных дат выполняется после входа владельца, затем при возвращении вкладки на экран и раз в минуту в открытой вкладке. Уникальный ключ экземпляра `(seriesId, YYYY-MM)` исключает повторы. У остальных ролей просроченные записи видны, но системная автопроводка не выполняется. Ручная оплата уменьшает непокрытый остаток экземпляра; его полное исполнение или явное закрытие подавляет повторную автопроводку. Для автопроводки остатка использовать один идемпотентный ключ на экземпляр и текущую версию исполнения, не обходить проверку актуального остатка.

Правка серии: «Только этот платеж» или «Этот и будущие». Фактическое прошлое не меняется. Отмена серии прекращает только будущие неисполненные экземпляры. Уже просроченные записи пользователь разбирает отдельно, приложение не удаляет их без решения.

Месячные лимиты: общий и по расходной категории, в RUB, необязательные. Базовые значения повторяются, можно переопределить конкретный месяц. Остатки не переносятся. Предупреждения при 80% и 100%; превышение не блокирует ввод. Общий лимит уже включает категории, их остатки не складываются с ним. Возвраты уменьшают расход месяца возврата. При расходе ниже нуля после возвратов показать это текстом, индикатор ограничить диапазоном 0–100%.

Прогноз денежного баланса на дату = фактические денежные остатки на сегодня + еще не исполненные остатки плановых поступлений − еще не исполненные остатки плановых списаний до выбранной даты. Это прогноз денег на кошельках, не свободной от резервов суммы. Депозитные выплаты и кредитные платежи включаются через связанные планы, не второй раз. Прогноз не меняет текущий баланс и подписан «При исполнении плана; курсы без изменений». Просроченные остатки показывать отдельно и включать в обязательства; просроченные поступления включать в прогноз только с предупреждением «Срок получения прошел». В месячном прогнозе нельзя второй раз добавлять уже полученный доход. Для частичного исполнения вычитается/прибавляется только остаток.

## 10. Цели и резервы

Типы цели: покупка/накопление и досрочное погашение кредита. Поля: название 1–100 символов, целевая сумма, валюта, срок или комфортный взнос, приоритет 1–3, комментарий, статус active/paused/completed/archived. Несколько целей одновременно, без искусственного ограничения.

Резерв — часть остатка конкретного кошелька в его валюте, закрепленная за целью. Нельзя зарезервировать больше положительного свободного остатка кошелька. Одна единица денег не может принадлежать двум резервам. Уже накопленное при создании цели назначается из существующего остатка, не вводится как новые деньги. Для цели в другой валюте прогресс пересчитывается через последние ручные RUB-курсы; отсутствующий курс делает расчет неполным.

Пополнение/освобождение резерва не является доходом/расходом. Для траты зарезервированных денег обязательно выбрать цель и освобождаемую сумму; расход и освобождение атомарны. При обычном расходе, затрагивающем резерв, показать предупреждение и потребовать указать освобождаемый резерв; нельзя оставить резерв больше остатка. Перевод зарезервированных средств переносит резерв на получающий кошелек, при обмене — пропорционально фактической полученной сумме. Комиссия оплачивается из свободных денег или явно выбранного освобождения резерва.

Депозит не может выступать источником резерва цели. Возврат с депозита сначала зачисляется в кошелек, после чего пользователь при желании резервирует деньги. Инвестиционные виды не связаны с целями.

### 10.1. Расчет «К дате»

Осталось R = max(0, стоимость цели − текущая оценка резервов в валюте цели). Пользователь задает ежемесячный день взноса и дату первого взноса не раньше сегодняшнего дня. Для отсутствующего числа месяца использовать последний день месяца. N — число предстоящих дат взноса не позже срока. Месячный взнос = ceil до минимальной единицы валюты от R/N, последний взнос — остаток. При N=0 показать необходимый разовый взнос R до срока. При сроке в прошлом и R>0 показать «Срок прошел», без отрицательных месяцев.

Справочный дневной взнос = R / число оставшихся календарных дат, считая сегодня и дату срока; недельный = дневной × 7. Это альтернативные эквиваленты, не дополнительные обязательства. Срок сегодня означает один день. Уже достигнутая сумма показывает 100% и нулевой взнос.

### 10.2. Расчет «В комфортном темпе»

Месячный взнос задается фиксированной суммой в валюте цели или процентом 0–100 от ожидаемого месячного дохода семьи в RUB. Этот доход — отдельный явно заданный параметр, не сумма текущих счетов и не скрытая оценка зарплаты. Процентный взнос переводится в валюту цели по ручному курсу.

Число взносов = ceil(R / месячный взнос). Прогноз — дата последнего взноса из ежемесячного расписания. Нулевой взнос дает «Срок не рассчитан». Нулевой/незаданный ожидаемый доход отключает проценты. Доля фиксированного взноса = RUB-эквивалент взноса / ожидаемый доход × 100%; возможное значение выше 100% показывается как предупреждение.

Показывать общую месячную потребность всех активных целей и сопоставлять ее с ожидаемым доходом за вычетом запланированных расходов. План взносов не переводит деньги автоматически и не увеличивает резервы. При паузе резервы остаются, будущие взносы перестают участвовать в доступной сумме. При архивировании сначала освободить резервы с подтверждением.

### 10.3. Цель погашения кредита

Связь с выбранным кредитом только для оценки необходимой суммы и сценария досрочного погашения. Предложить текущий основной долг, но сохранить выбранную пользователем целевую сумму отдельно; показать расхождение при изменении долга. Резервы не уменьшают кредит до фактического платежа. Кнопка «Направить на погашение» открывает форму досрочного платежа, освобождает выбранный резерв и проводит реальный платеж атомарно.

## 11. Депозиты

Вклад необязателен: пустой раздел предлагает «Добавить депозит». Не создавать его автоматически. Поддержать фиксированную или меняющуюся по датам годовую ставку, пополнение и частичное снятие, капитализацию или выплаты на кошелек, выплату в конце срока. Выбор условий делается отдельно для каждого вклада.

Поля: название, банк/организация, валюта, дата открытия, дата окончания, основной остаток, ставка или интервалы ставок, способ выплаты monthly/end, капитализация yes/no (при end — только нет), день ежемесячной выплаты (по умолчанию день открытия), счет выплаты в той же валюте, разрешение пополнения, разрешение частичного снятия, неснижаемый остаток, ставка досрочного закрытия, комментарий.

Два режима добавления:

- Новый вклад: сумма переводится с кошелька на депозит; это внутреннее перемещение, не расход. Дата не раньше начала учета.
- Уже существующий: основной остаток на дату начала учета добавляется как отдельный стартовый актив, не доход. Пользователь подтверждает, что эти деньги не дублируются в стартовых кошельках. Можно задать начисленные, но еще не выплаченные проценты до начала учета как отдельную начальную справочную величину; они не считаются доходом до выплаты.

### 11.1. Расчетная модель

Использовать ACT/ACT: за календарный день проценты = основной остаток на начало дня × годовая ставка / 100 / (365 или 366 дней в году). Для нового вклада первый день начисления — день после внесения, последний — день закрытия включительно. Для существующего — первый день учета; ранее накопленное задается отдельно. Пополнение и снятие, проведенные сегодня, меняют базу со следующего дня. Ставка нового интервала действует с указанной даты; интервалы не перекрываются и покрывают весь срок.

Проценты капитализируются только в даты фактического подтверждения капитализации, с базой начисления со следующего дня. При ежемесячных выплатах использовать день открытия с правилом конца короткого месяца. Дата первой выплаты строго позже открытия; в дату окончания выплачивается остаток процентов. Деньги не зачисляются дважды при совпадении месячной выплаты с закрытием.

Расчет — оценка по выбранной модели, не точное воспроизведение любого банковского договора. Рядом с формулой указать модель и возможность подтвердить фактическую сумму банка. Налоги не рассчитываются: прогноз и доход показываются до налогов; реально удержанный налог можно отдельно записать расходом.

### 11.2. Действия и фактический учет

Владелец может: открыть, внести дополнительную сумму, снять часть, подтвердить выплату процентов, подтвердить капитализацию, закрыть в срок, закрыть досрочно. Пополнение и снятие допустимы только если разрешены условиями. Частичное снятие не ниже неснижаемого остатка; полное — через закрытие. Валюты кошелька и вклада должны совпадать, иначе сначала отдельный обмен.

По умолчанию рассчитанные проценты не проводятся автоматически: отображается начисленная оценка и ближайшая дата. Владелец подтверждает рассчитанную или фактическую сумму. Выплата процентов = доход на кошелек; капитализация = доход, увеличивающий основной остаток вклада. Начальная сумма и возврат основного остатка — не доход. В общий баланс включается только основной остаток с подтвержденной капитализацией, не расчетные невыплаченные проценты.

У каждой выплаты/капитализации есть кнопка «Сверить с банком»: дата, расчетная сумма, фактическая сумма из выписки, разница и необязательная причина. Для неподтвержденного события сохраняется фактическая сумма без дополнительного дублирующего начисления. Для уже проведенного события выполняется исправление его ревизии и связанного дохода/остатка в одной транзакции, а не новое начисление всей суммы. История хранит расчет и факт отдельно. При изменении фактической капитализации будущая база пересчитывается со следующего дня; зависимые уже подтвержденные последующие события автоматически не переписываются — показать их и потребовать последовательной сверки/отмены, как для иных зависимостей. Ручная сверка не заменяет ACT/ACT в прогнозе и не изменяет годовую ставку скрыто.

Досрочное закрытие: показать предварительный пересчет всех процентов по заданной ставке досрочного закрытия за фактические дни и разницу с уже выплаченными процентами. Для вкладов с капитализацией пересчитать историю по той же модели со ставкой досрочного закрытия. Итоговая сумма возврата = основной остаток + невыплаченный расчетный результат − удержание излишне выплаченных процентов. Пользователь обязательно подтверждает фактический возврат банка и сумму удержания; отрицательный возврат не допускается без отдельной ручной корректировки условий. Корректировка ранее признанного процентного дохода отражается отдельной отрицательной строкой дохода, не скрытым расходом. Ее не учитывать как возврат покупки.

После закрытия остаток вклада нулевой, деньги на выбранном кошельке, статус closed; история доступна. Автопролонгация в первой версии не нужна: новый срок — новый депозит.

Карточка: основной остаток, ставка/текущий интервал, срок и оставшиеся дни, подтвержденный процентный доход, расчетно начислено, прогноз до окончания при отсутствии новых движений, ближайшая выплата. Предстоящие выплаты можно включать в прогноз, но не в текущие доступные деньги. Депозиты не используются как резерв целей.

## 12. Кредиты и личные долги

### 12.1. Банковский кредит

Поля: название, кредитор, валюта, исходная сумма, дата выдачи, основной долг на начало учета (для существующего), начисленные непогашенные проценты на начало учета (необязательно), годовая фиксированная ставка 0–1000%, тип annuity/differentiated, оставшийся срок 1–600 месяцев, дата первого планового платежа, день платежа, кошелек оплаты, необязательные регулярные комиссии/страховка, комментарий.

Новый кредит зачисляет сумму на кошелек как заемные средства, не обычный доход. Существующий кредит создает начальный долг без зачисления денег второй раз. Известную переплату до начала учета вводить отдельным справочным полем; отчеты текущего учета ее не включают. Цель — видеть долг и переплату, а не воспроизводить все банковские продукты: плавающая ставка, льготные периоды и кредитные карты со сложными правилами отложены.

Расчетный график по месяцам: r = годовая ставка / 100 / 12; n = число оставшихся платежей; P = остаток основного долга. Аннуитет A = P × r / (1 − (1+r)^(-n)), при r=0 — P/n. Дифференцированный платеж: основной долг P/n плюс проценты на остаток перед платежом. Округлять строки до точности валюты, последний платеж корректирует остаток до нуля. Платежный день обрабатывается по правилу короткого месяца.

Это модель равных месячных периодов; отдельная подпись «Расчетный график, может отличаться от банка». Неполный первый месяц, штрафы за просрочку и ежедневная банковская модель автоматически не вычисляются. Даты управляют расписанием, не меняют месячную формулу. Пользователь может подтвердить фактическую разбивку банка.

Для существующего кредита просроченные начисленные проценты на начало учета идут отдельной обязанностью в ближайшем платеже сверх новой расчетной строки; не входят в P. При внесении фактической выплаты эти проценты гасятся первыми.

Платеж содержит общую сумму, часть основного долга, проценты и комиссии; сумма частей строго равна списанию. Только основной долг уменьшает обязательство. Для семейного бюджета весь платеж — денежный расход категории «Кредиты», с детализацией «тело / проценты / комиссии». Переплата — только проценты и связанные комиссии/страховка, без тела кредита. Нельзя одновременно провести эту же выплату обычным расходом и кредитным платежом.

Плановые строки кредита создают обязательства и появляются в календаре. При оплате строка связывается с фактом. Просрочка показывается, но штрафы не выдумываются; их можно добавить фактической комиссией. Излишек платежа сверх остатка долга запрещен, если отдельно не указана комиссия.

### 12.2. Досрочное погашение

Владелец выбирает дату, кошелек, сумму уменьшения основного долга и режим: «Уменьшить срок» или «Уменьшить платеж». По умолчанию досрочный платеж отдельно от регулярного; если есть непогашенные начисленные проценты, показать их отдельным полем и включить в общую сумму списания.

Перед сохранением показать старый и новый график, оставшиеся платежи, дату окончания, будущую переплату и расчетную экономию. При уменьшении платежа сохранить оставшееся число платежей и пересчитать A для нового P; при уменьшении срока сохранить прежний A и симулировать месяцы до нулевого остатка с меньшим последним платежом. Для дифференцированного кредита при уменьшении срока сохранить прежнюю месячную часть тела, при уменьшении платежа распределить новый остаток на прежнее оставшееся число платежей.

Плановые будущие строки заменяются новым графиком; фактические платежи неизменны. Досрочный платеж не оплачивает следующий регулярный автоматически. Если основной долг и начисленные обязательства равны нулю, кредит закрывается и будущие планы отменяются. Отменять более ранний кредитный платеж можно только после отмены последующих зависимых выплат, с объяснением порядка.

### 12.3. Личные займы

Два вида: «Мы должны» и «Нам должны». Поля: контрагент, валюта, сумма/остаток, дата возникновения, срок возврата по желанию, счет выдачи/получения, комментарий. Для существующего долга — остаток без нового денежного движения. Для нового — фактическая выдача или получение.

Новый заем семье увеличивает деньги и долг, но не доход. Выдача займа уменьшает деньги и создает требование, но не бытовой расход. Возврат тела долга не считается доходом/расходом; отдельно показывается в денежных движениях. Полученные проценты — доход, уплаченные — расход. В этой версии для личных займов нет автоматического процентного графика: сумму процентов вводят при выплате. Частичные возвраты разрешены, отрицательный остаток запрещен.

Отдельные карточки: основной долг, проценты/переплата за время учета, ближайший платеж, просрочка, расчетная дата закрытия. Долги семьи не вычитаются из главного общего баланса: он показывает активы, а не чистый капитал. В разделе долгов явно показывать обязательства и требования отдельно. Дебиторские требования не считать доступными деньгами.

## 13. Инвестиции: настройка для будущего развития

Отдельного пункта навигации и пустого экрана «Инвестиции» в первой версии нет. В настройках есть свернутый блок «Интересующие инвестиции» с необязательным выбором «Акции», «Облигации», «Фонды». Это сохраняет пожелание пользователя выбирать виды, не загружая основной интерфейс заглушкой. Выбор меняет только владелец, остальные видят его в доступном для чтения виде.

Сохранить массив выбранных кодов в family.investmentInterests; отдельное хранилище investmentPreferences не создавать. Если пользователь блок не открывал, он не требует заполнения. Рядом коротко указать, что учет этих инструментов в текущую версию не входит. Выбор не создает активов, сумм и проводок. Не показывать неработающие формы покупки, котировки, фиктивную доходность или нулевой портфель как будто он рассчитан. Все депозитные функции описаны отдельно и не урезаются из-за отложенных инвестиций.

## 14. Главный экран и формулы сводных показателей

Дизайн главного экрана сохраняет две главные карточки. Не заменять их тремя карточками активов/ликвидности/трат.

Обозначения в RUB по актуальным ручным курсам:

- W — сумма всех фактических остатков кошельков.
- D — основной остаток активных депозитов, включая подтвержденную капитализацию.
- L — сумма остатков кошельков с флагом доступности для текущих расходов.
- R — часть резервов целей на доступных кошельках.
- O — только неисполненные остатки обязательств и явных расходных планов до конца текущего месяца, включая просроченные; кредитные платежи учитываются один раз. Лимиты категорий и уже исполненные части плана в O не входят.
- G — оставшийся на месяц план взносов по активным целям.

**Общий баланс B = W + D.** Под суммой раскрытие: кошельки, вклады, дата курсов. Невыплаченные проценты, предполагаемая прибыль, личные требования и будущие доходы не включаются. Подпись: «Сейчас, активы без вычета долгов».

**Можно потратить A = L − R − O − G.** Подпись: «До конца текущего месяца, без будущих поступлений». Недоступные кошельки и депозиты исключены через L. Обязательства учитываются независимо от выбранного кошелька, так что нехватка ликвидности видна. Отрицательное A показывается как «Не хватает …», не обрезается до нуля. Категорийные лимиты не вычитаются повторно как обязательства.

Инвариант против двойного учета: при оплате связанного плана из ликвидного кошелька на X ликвидный остаток L уменьшается на фактическое списание, а непокрытое обязательство O в той же транзакции уменьшается на покрытую часть плана. В одной валюте и при неизменном курсе, если факт равен покрытой части, A не уменьшается повторно. Отличие факта от плана и переоценка валют показываются отдельно. Обычная неплановая трата уменьшает L и A один раз. Нельзя при каждой покупке уменьшать фактический баланс, оставляя ту же оплаченную часть в O. При оплате из кошелька, не включенного в L, доступная сумма может увеличиться вследствие снятого обязательства; расшифровка показывает источник оплаты, это не новое поступление.

В раскрытии карточки дополнительно показать «Свободно сейчас = L − R» и «При получении ожидаемых доходов = A + E», где E — неисполненные плановые денежные поступления до конца месяца по текущим курсам. Это справочные строки внутри раскрытия, не замена двух главных карточек. У второй строки подпись «Сценарий, не доступные сейчас деньги»; просроченные поступления явно отмечены. Депозитная капитализация не входит в E, выплата на доступный кошелек входит. Поступление на недоступный кошелек в E этой строки не включается.

Для G используется план месяца за минусом чистых пополнений резервов этой цели в этом месяце, но не меньше нуля; освобождение резерва уменьшает чистое пополнение. Для начальных резервов, заданных при создании цели, месячный взнос не считается выполненным автоматически: в форме отдельно предложить «Считать взносом текущего месяца». Это исключает скрытый двойной учет.

Плановый расход, который будет оплачен из уже зарезервированных денег цели, может явно ссылаться на резерв. Тогда в O включается только часть, не покрытая этим резервом; покрытие не может одновременно принадлежать двум планам. Остальное обязательство вычитается целиком. Когда операция оплачена, она уменьшает фактический баланс, освобождает резерв и исключается из O атомарно.

При отсутствии курсов B/A подписаны как неполные; не показывать точное «можно потратить» без предупреждения. Все части формулы можно раскрыть до списков счетов, резервов и платежей. Карточки B/A всегда текущие и не меняют смысл при выборе старого отчетного периода.

Ниже: доходы, расходы и их разница за выбранный период; ближайшие платежи; лимиты; прогресс целей; три графика; последние операции. Заемные средства, возврат тела займов и внутренние переводы выводятся отдельными строками движения денег, а не смешиваются с заработком.

## 15. Периоды, графики и сверка

Переключатель «День / Неделя / Месяц / Год», стрелки назад/вперед, «Текущий период», явный диапазон дат. Неделя — понедельник–воскресенье, год календарный. Дневной график по часам, недельный по дням, месячный по дням, годовой по месяцам. Если дата операции была введена без времени, использовать 12:00 и обозначать время как условное при просмотре.

Кольцевая диаграмма расходов использует чистые расходы категорий за период. Для отрицательной категории после возвратов не рисовать отрицательный сектор: отдельная строка «Возвраты сверх трат периода», сектор из max(0, чистый расход). Легенда показывает фактические значения и объясняет разницу с общей суммой. Доли диаграммы считать от суммы положительных секторов.

Столбцы доходов/расходов показывают фактические рублевые суммы по датам. Возвраты и коррекции дохода допускают отрицательные значения; ось должна их отображать. План отдельно пунктиром или переключателем, без суммирования с фактом. График цели показывает накопленное и план по датам; суммы в валюте цели с обозначением допущения курса.

Сверка активов за период: начальная оценка активов + доходы − расходы + прочие внешние денежные движения + переоценка = конечная оценка активов. Прочие движения включают выдачу/возврат личных займов и полученные кредиты; кредитное тело уже находится в расходах семейного бюджета и вторично не вычитается. Переводы на депозит и между кошельками внутри активов равны нулю за исключением комиссий и изменения оценки валют. Сверку показывать в деталях, а не требовать равенства изменения баланса одной разнице доходов/расходов.

У графиков текстовые итоги, легенда, подписи и доступное представление таблицей. Пустое состояние без случайных демоданных. Фильтр диапазона отчета не скрывает текущие системные предупреждения о нехватке средств.

## 16. Голосовой ввод

Использовать Web Speech API SpeechRecognition или совместимый префикс, язык `ru-RU`. Возможность проверять при запуске, а не по имени браузера. Микрофон включается только по нажатию. Остановить по кнопке, при получении законченной команды, выходе/блокировке профиля или после 30 секунд.

Обрабатываются только доходы и расходы. Примеры обязательных фраз:

- «Магазин продукты потрачено 650 рублей» → расход, продукты, 650 RUB, сегодня.
- «Одежда ребенку 5000 рублей» → расход, одежда, отметка ребенка.
- «Вчера получила зарплату 80 тысяч рублей» → доход, зарплата, вчера, 80000 RUB.
- «Подарок 100 долларов» → доход, подарок, 100 USD; если тип неоднозначен, запросить выбор.
- «Непредвиденные расходы ремонт 3000 рублей» → расход, непредвиденные, комментарий «ремонт».

Обязательный парсер ограничен простыми подсказками: цифры и десятичные числа в распознанном тексте, цифровая сумма с множителем («80 тысяч», «1,5 миллиона»), слова «сегодня», «вчера», «позавчера», синонимы валют, готовый словарь категорий и имен членов семьи. «Аванс/отпускные/зарплата/получила/получил» подсказывают доход; «потратила/потрачено/купил/купила» — расход. Противоречивые признаки требуют выбора пользователя. Сопоставление категорий — по явным словам/синонимам, без обещания понимания свободного финансового языка.

Полный разбор словесных числительных («восемьдесят две тысячи триста сорок пять»), сложных дат, нескольких трат в одной фразе и произвольных грамматических конструкций не входит в обязательный объем. Если сервис выдал такую строку вместо цифр, сохранить ее видимой в форме и попросить уточнить сумму. Для неполного разбора уже уверенно распознанные поля сохраняются, остальные заполняются вручную; голосовой ввод не исчезает из продукта. Кнопка не сохраняет запись по одной уверенности парсера.

Если счет не назван, предложить отмеченный владельцем основной счет нужной валюты; если его нет или счетов несколько без основного — потребовать выбор. Валюта без упоминания — RUB, дата без упоминания — сегодня. Неизвестная категория — «Прочее» с подсветкой для проверки. При нескольких суммах или нескольких операциях не разбивать автоматически: предложить одну запись за команду или ручное распределение.

Всегда показать текст распознавания и редактируемую форму перед сохранением. Сумма и счет обязательны, подтверждение явно. Для роли с подтверждением кнопка называется «Отправить на подтверждение».

Ошибки: нет поддержки → ручной ввод; отказ микрофона → объяснение и повтор; нет речи/сеть → повтор без потери заполненной формы; неясная сумма/дата/счет → заполнение поля. Не сохранять аудио. Распознавание может выполняться внешним сервисом браузера и требовать интернета; перед первым использованием сообщить это кратко. Полностью локальное распознавание не обещать.

## 17. Дизайн и удобство

Спокойная современная семейная финансовая панель. Приоритет суммам и действиям, без пестрых иллюстраций, фотографий, ярких градиентов и избыточной анимации.

Визуальное направление после обратной связи: глубокий синий, теплый светлый фон, мягкие персиковые, мятные и лавандовые акценты; более выразительная типографика и композиция при сохранении спокойного характера. Светлая тема: фон `#F7F5F2`, карточки `#FFFFFF`, текст `#202B42`, основной акцент `#425B99`. Темная: фон `#111827`, карточки `#1C2639`, текст `#F0F2FA`, акцент `#B0C1EF`. Навигация — темно-синяя `#19263E`, карточка баланса — глубокая синяя; доступная сумма выделена мягким персиковым фоном. Доходы обозначаются спокойным зеленым, расходы — терракотовым, предупреждения — охристым. Допустимы тонкие фоновые линии и мягкие цветовые переходы без яркости. Контраст проверить и при необходимости скорректировать оттенок; не обозначать смысл только цветом.

Боковая панель 220–240 px, шапка, содержимое с максимальной шириной около 1440 px, интервалы кратны 4/8 px, карточки со скруглениями 12–16 px, тонкие границы. Основной текст не меньше 14 px, суммы главных карточек 32–40 px, системный шрифт с табличными цифрами.

Приемочные размеры: 1280×720 и 1920×1080. На 1024 px допустимы компактная навигация и локальный горизонтальный скролл таблиц, но основные кнопки доступны. Мобильный интерфейс специально не проектируется. Все формы управляются клавиатурой, видимый focus, Escape закрывает окно с проверкой несохраненного, Tab не уходит за модальную форму, после закрытия фокус возвращается на кнопку открытия. Ошибки и статусы доступны через aria-live.

Переключатель темы действует сразу. Тема хранится у профиля; до входа — последнее локальное предпочтение, при первом запуске — светлая. Загрузка сохраненных данных не должна мигать тестовыми суммами. Для длительных операций показать индикатор, повторную кнопку временно блокировать.

### 18.1. Конкурентные вкладки и сбои

Одновременные действия двух вкладок не должны терять записи. IndexedDB readwrite-транзакция перечитывает revision семьи/сущности, проверяет права и остатки, увеличивает revision. При конфликте отменить действие с предложением обновить форму. BroadcastChannel сообщает об обновлении/блокировке; fallback — storage-сигнал. У каждой команды UUID idempotencyKey, уникальный индекс; повторный клик/повтор обработки возвращает прежний результат, не создает дубликат.

Ошибки quota/storage/transaction показывать как «Не удалось сохранить», сохранять форму в памяти и предлагать повторить; не очищать БД автоматически. Закрытие вкладки во время записи либо завершает целую транзакцию, либо оставляет прежнее состояние. При недоступном IndexedDB нельзя имитировать успешное сохранение только в памяти.

При обновлении версии схемы нужны последовательные миграции без удаления существующих данных. Если БД открыта более новой версией, заблокировать запись и предложить обновить страницу. Можно запросить persistent storage после явного завершения настройки; отказ не блокирует работу. При очистке данных браузером восстановление из облака не обещать.

### 23.1. Денежные группы и аналитические типы

### 23.2. Отмена и исправление операций с резервом

Форма расхода показывает свободную и зарезервированную части счета. При недостатке свободной части сначала требуется освобождение конкретного резерва. Если даже после освобождения денег недостаточно, отдельное подтверждение отрицательного остатка доступно только владельцу/прямому участнику. Для роли с подтверждением решение принимает владелец при одобрении.

Нельзя оставить положительный резерв на кошельке с отрицательным остатком. Любой перевод резерва требует явного выбора цели и суммы; необязательно переносить все резервы счета. Отмена связанной группы восстанавливает резерв, если средства для него еще доступны; иначе сначала исправляются зависимые последующие операции. Автоматически брать деньги из другой цели запрещено.

### 23.3. Депозит: расчетный результат досрочного закрытия

Для вклада, открытого в период учета, выполнить теневой расчет: те же реальные пополнения/снятия и даты, но ставка досрочного закрытия вместо обычных ставок; в даты капитализации теневой расчет капитализирует собственные пересчитанные проценты. Это определяет общие допустимые проценты I_early за фактический срок. Фактические внешние выплаты обозначить I_paid, фактически капитализированные суммы I_cap. Не включать I_cap в I_paid.

Расчетный возврат = текущий фактический основной остаток − I_cap + I_early − I_paid. Проценты к доплате/удержанию = I_early − I_paid − I_cap. При отрицательной разнице создать уменьшение ранее признанного процентного дохода, при положительной — дополнительный доход. Таким образом начисления не считаются дважды. Окончательную сумму и удержание банк подтверждает через пользователя; приложение допускает корректировку с причиной и сохраняет расчет рядом с фактом.

Для существовавшего до старта вклада полная история пополнений и выплат неизвестна: не обещать точного досрочного пересчета за весь срок. Показать расчет за известный период отдельно, а фактические возврат и удержание потребовать вручную. В доход/корректировку текущего учета включать только разницу, подтвержденную сейчас; начальный невыплаченный процент учитывается при выплате отдельной строкой с указанием происхождения.

В обычном закрытии пользователь вводит отдельно возврат тела и проценты; сумма поступления равна их сумме за вычетом явных удержаний. Для капитализированного вклада тело уже содержит ранее признанные проценты, повторно доходом они не становятся. Нельзя редактировать ставку задним числом поверх подтвержденной выплаты: сначала отменить зависимые выплаты или внести новую ставку на будущую дату.

### 23.4. Кредит: отличие фактического платежа от плана

Регулярный платеж закрывает одну строку графика. В первой версии частичная оплата одной плановой строки не поддерживается: пользователь подтверждает полную фактическую разбивку банка. Дополнительный платеж в ту же дату оформляется отдельным досрочным платежом, не второй оплатой строки.

Фактические проценты/комиссии могут отличаться от расчетных. Если фактическое тело соответствует плановому, следующие суммы тела и сроки остаются по графику. Если фактическое тело отличается, после оплаты пересчитать будущий график от фактического остатка, сохранив прежние оставшиеся даты и их количество; показать новое расписание перед подтверждением. Если оставшихся дат нет, но основной долг остался, требуется выбрать новый оставшийся срок, платеж не фиксируется со скрытым незакрытым остатком.

Основное тело не может превышать остаток долга. Расчетное обслуживание просрочки не меняет ставку и не начисляет выдуманные штрафы: фактическая сумма приходит от пользователя. Текущие подтвержденные проценты и прогноз будущей переплаты всегда отдельные показатели. Экономия досрочного погашения считается только относительно одного и того же текущего графика, без учета прошлых уже уплаченных процентов.

Степени в аннуитетной формуле рассчитывать фиксированной арифметикой с промежуточной точностью не менее 18 знаков и последующим денежным округлением. Проверять сумму тела по графику: она равна исходному остатку, а последний остаток строго ноль.

### 23.5. План, задолженность и доступные деньги

Платежи кредитов и депозитные поступления используют общую сущность plans со ссылкой на модуль. Создание вручную второй плановой записи для той же выплаты не происходит. Связи с фактом сохраняются через planLinks: обычный план поддерживает несколько частичных исполнений, договорная строка кредита — одно полное исполнение согласно разделу 23.4. В планах только настоящие денежные поступления/списания: капитализация вклада увеличивает актив, но не прогноз ликвидного кошелька.

В O используется остаток плана, а не его исходная сумма. Покрытие резервом цели ограничено этим остатком; оплаченная из резерва часть одновременно уменьшает активное reserveCoverage и сам резерв. Нельзя сохранять старое покрытие на уже оплаченную часть и применять его второй раз к другому обязательству. Для одного резервируемого остатка поддерживается только одно активное назначение покрытия.

Плановые выдачи личного займа, открытие и пополнение вклада вручную не планируются в первой версии: это фактические действия. Обязательства возврата личного займа семьи включаются в O, когда срок задан; возврат требования семьи включается в прогноз только при явно созданном ожидаемом поступлении, а не просто потому, что должник назван.

Если у цели нет месячного взноса (например, она на паузе), G по ней равен нулю. При нескольких валютах пересчитывать G/R/O по текущим ручным курсам; прогноз подписывать как зависимый от них. Приоритет цели влияет только на сортировку и видимые рекомендации пользователя, автоматического распределения денег по приоритетам нет.

### 23.6. Права на планы и заявки

Участник может подтвердить только обычный доходный/расходный план, который не является платежом кредита, личного долга или депозитной выплатой. Эти договорные операции проводит только владелец. Если участнику нужно изменить будущий план или платеж другого автора, он подает запрос владельцу. Не разрешать обход прав через универсальную форму «Расход» для операции, уже связанной с кредитным графиком.

Разрешенный лимит прав определяется по текущей роли, не по роли в момент открытия формы. При смене роли/блокировке аккаунта сохраняемые черновики не получают прежних привилегий. В журнале системной автопроводки actorId=`system`, отдельно хранится ownerId, запустивший обработку.

## 24. Решения по внешней проверке требований

Редакция 1.1. Принятые изменения встроены в основные разделы, модель данных и приемочные примеры; этот раздел объясняет решения, а не вводит параллельное противоречащее ТЗ.

| Замечание | Решение и причина |
|---|---|
| Удалить голос или упростить парсер | Принято частично: голос — исходное требование пользователя, поэтому остается; обязательный парсер ограничен простыми полями и подсказками. Полный разбор числительных и свободного языка исключен. Ограничения браузера и ручная проверка уже учитывались. |
| Удалить инвестиционные заглушки | Принято частично: пустой экран и отдельное хранилище убраны. Необязательный выбор трех видов сохранен в свернутых настройках, поскольку пользователь явно его просил. |
| Удалить аудит, оставить только отмену последней записи | Замена не принята: семье нужно разбирать, кто внес ошибку, а отмена последнего действия не решает зависимые платежи. Принято уменьшение объема: журнал хранит ссылки/измененные поля вместо полных снимков; UI-события не журналируются. |
| Разрешить модульную разработку и сборщик | Принято для разработки. Пользователь по-прежнему получает страницу из трех готовых файлов без установки зависимостей и сборки при запуске. Исходники и команда сборки сохраняются отдельно. |
| Добавить экспорт/импорт JSON | Полезное направление, но не включено в первую версию: пользователь явно утвердил отсутствие экспорта/импорта. Зафиксировать в будущем плане резервное копирование с версионированием, проверкой целостности, правами и восстановлением; не добавлять наполовину реализованную кнопку. Риск потери локальных данных остается явно указанным. |
| Добавить прямые кросс-курсы | Принято как уточнение: фактический обмен уже опирался на A/B; теперь явно запрещен промежуточный пересчет сделки через RUB. USD→EUR работает и без справочных RUB-курсов; они нужны только оценке отчетов. |
| Отделить банковские комиссии | Принято: bank_fees и other_fees, фильтр комиссий, явное снятие наличных как перевод. Все реальные комиссии входят в общий расход, но не дублируются в кредитном платеже. |
| Заменить формулу доступной суммы | Полная замена не принята: O уже означает неоплаченные обязательства, а не весь исходный план. Усилены связи плана с фактом, частичное исполнение и атомарное уменьшение остатка; добавлены числовые тесты. Справочные «свободно сейчас» и сценарий ожидаемых доходов доступны в раскрытии. Два главных показателя сохранены. |
| Заменить роли общим PIN и убрать PBKDF2 | Не принято: разные права и авторство — прямое требование пользователя. PIN этого не заменяет; слабая защита локального интерфейса и безопасное хранение пароля — разные вопросы. Уточнено, что PBKDF2 уже вызывается через асинхронный Web Crypto только при работе с паролем. Возможность обхода локального UI не скрывается. |
| Заменить дневной расчет вклада ручной суммой | Принято частично: ACT/ACT остается воспроизводимой моделью прогноза, а не обещанием банковской точности. Ручное подтверждение факта уже предусматривалось; добавлены явная кнопка сверки, разница расчет/факт и правила исправления без повторного начисления. |

Резервное копирование рекомендуется обсудить перед использованием приложения как единственного реального семейного учета. Текущая редакция не отменяет сознательно выбранное ограничение пользователя. Полный сброс БД, обход пароля владельца через сброс и автоматическая очистка финансовой истории не добавлены.

## 25. Уточнения по обратной связи пользователя к этапу 1

Редакция 1.2 от 17 октября 2026 года. Пользователь отклонил первоначальную зеленую палитру и перегруженный стартовый экран. Новое направление и сценарий регистрации встроены в разделы 3–5, 17 и UC-01.

- Не запрашивать название семьи и имя владельца при старте. Имя профиля автоматически равно логину; отдельные права участников и авторство операций сохраняются. Редактирование подписей профилей и пометок внутри бюджета не удаляется.
- Не предлагать пользователю часовой пояс: сохранять автоматическое определение как внутренний параметр дат. Старые значения и финансовую историю не сбрасывать.
- В регистрации четыре поля: логин, пароль, повтор пароля, дата начала учета. Дату по-прежнему выбирает пользователь, без автоматического заполнения.
- Первый кошелек не является необязательной частью регистрации. После регистрации приложение сразу открыто; кошельки и их начальные остатки вводятся отдельным понятным действием внутри. Поддержка типов, валют и количества кошельков сохраняется.
- Пользователь может открыть и проверить все готовые разделы этапа 1 после входа: обзор, операции, кошельки и настройки. Нельзя выдавать еще не реализованные этапы за доступные функции. Демонстрационный бюджет с вымышленными средствами не добавляется в реальное хранилище.
- Техническая модель может сохранять внутреннее поле family.name для совместимости со старой БД; его наличие не требует пользовательского названия или поля в интерфейсе. Обновление внешнего вида не является миграцией или обнулением бюджета.
